# Rubric: is this pull request ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| plan-fidelity | The diff's changed files and hunks, read against the plan's scope, files list, approach, not-in-scope list, and deviation notes; then the description's claims about what changed, read against the diff. | Pass if (a) every behavior change in the diff is one the plan or its deviation notes name (helpers, regression tests, comments, imports, and changelog entries that serve the planned change count as inside it), (b) every deliverable the plan commits to is in the diff, or its absence is stated as a deferral or deviation in the plan and again in the description, and (c) the description claims no change the diff lacks and denies no change the diff contains. Fail if the diff adds unplanned work (a new flag, option, setting, renamed members, a rewrite of a function or file the plan never names, reworded unrelated text), drops a planned deliverable without saying so, or the description says "exactly as planned", "in full", "no changes beyond the plan" or describes a change (docs updated, file touched) that the diff contradicts. | required |
| decisive-evidence | The test evidence (and any before/after pasted in the description), read against the plan's test plan and repro: its trigger input, its expected-after, and every failure scenario it names; plus the reported outcome of the repo's own test suite or the test command the plan names. | Pass if all of these hold: (a) the plan's repro, with the same trigger input or scenario that showed the bug, is re-run on the branch and its after result is shown as output, a transcript, or a specific observed behavior that matches the plan's expected-after; (b) the before result is shown or stated (in the evidence or the description); (c) every distinct failure scenario the plan's test plan names is re-run (a control may be confirmed in one sentence); (d) the outcome of the repo's test suite or the plan's named test command is stated. A check that failed is still evidence if the failure is reported with its reason. Fail if the evidence is only a claim ("tested locally", "works now", "verified on my machine", "tests pass" with no repro output), if it re-runs only a control or a different input from the plan's repro (a path the fix never changed), if it skips a failure scenario the plan names, or if no suite or check result is reported. | required |
| clean-diff | Every hunk of the unified diff and the commit list, read against the change the plan describes. | Pass if every hunk is part of the fix, its tests, or a file the repo or plan asks for, and the diff carries none of the debris listed under Fail. Comments that explain the fix, and unchanged context lines shown inside a hunk that also changes the same statement, are fine. Fail if the diff contains any of: a debug print or log line (including a commented-out one), commented-out code or an earlier attempt left in, a dead or unused function or variable (including ones hidden behind `allow(dead_code)` or similar), a leftover TODO/FIXME, a hunk or block that only re-indents, reformats, reorders imports, or removes and re-adds identical lines, or an edit to code, text, or files unrelated to the fix. | required |
| repo-standards | The repo facts' PR-template asks, contributing-guide PR asks, and AI-use policy (live: `.github/PULL_REQUEST_TEMPLATE.md`, `docs/CONTRIBUTING.md`, and the course's AI-disclosure rule), read against the title, description, and diff. | Pass if every ask that applies to this PR is met: each section or checklist item the template names is present with real content (a heading, a label, or a plain statement that covers it, such as "fixes #123" for an issue-link ask); each file the repo asks a bug fix to include (a changelog or whatsnew entry) is in the diff; and, when the policy requires disclosure of all AI usage or of AI use in pull requests, the description says which AI tool was used and how much. An ask that does not apply (screenshots for a non-UI change, a new-feature rule for a bug fix) passes. With no template, no PR asks, and no AI-disclosure requirement, pass. Fail if a required section, checklist, or issue link is missing, a required changelog/whatsnew entry is absent from the diff, or a required AI disclosure is missing. | required |
| thread-engaged | The thread highlights (comments by OWNER, MEMBER, COLLABORATOR, or a maintainer-role CONTRIBUTOR), read against the description. | Pass if every explicit maintainer direction or open question in the thread is followed by the PR or named in the description with a reason it differs, or if the thread has no such direction. Fail if the PR heads elsewhere without mentioning it. | preferred |

## Verdict rule

Accept if every `required` check passes. Reject if any `required`
check fails. An `unclear` grade on a required check counts as a fail,
because a PR whose readiness cannot be shown from the package is not
ready to submit. `preferred` checks are reported but never change the
verdict, whatever their grade. A shortfall that the plan and the
description both disclose is not a fail on any check. The deciding
check for a reject is the first failing required check in table order.
