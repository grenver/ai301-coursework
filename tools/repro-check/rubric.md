# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| environment-recorded | The repro report's environment record (OS, tool/library version, and any config the issue names as relevant), read against the issue's own stated target version/platform. | Pass if the report names the OS and version(s) needed to place the attempt, and either matches the issue's target or explicitly names how it differs (e.g. "tested on 1.5.3, issue confirmed on latest/main"). Fail if no environment record exists at all, or if it silently diverges from the issue's target without saying so. | required |
| steps-followable | The repro report's steps, read as a stranger with no access to the reporter's machine, private repos, or local config would read them. | Pass if the steps are concrete commands/actions from a stated starting state through the actual trigger condition the issue names, using only inputs a stranger could obtain or recreate. Fail if a step depends on a private/unshared resource, skips the specific trigger condition (runs an adjacent variant instead of the one described), or is too vague to execute (no commands, no concrete inputs, no named starting state). | required |
| faithful-target | The artifact(s) in the repro report (output excerpt, log, screenshot), read against the specific behavior the issue describes, not a nearby or generalized symptom. | Pass if the shown artifact demonstrates the issue's exact reported behavior (same trigger, same failure mode/exit condition), or if the report honestly states it could not trigger that behavior and shows what happened instead. Fail if the artifact shows a different behavior (a different error type, a graceful failure instead of the reported crash, a different code path) while the report narrates it as confirming the issue. | required |
| evidence-backed | Every substantive claim in the claim comment and repro report (reproduced, could not reproduce, root cause), read against the artifacts or concrete observations shown to back it. | Pass if each claim is backed by a shown artifact or concrete observation, including an honest "I could not reproduce X" backed by a real attempt and a description of what was tried. Fail if a claim (a diagnosis, a "guaranteed" reproduction, a certainty about root cause) is asserted with no artifact behind it, or backed only by general enthusiasm or vibes ("this happens to me too", "obviously the X code is flaky"). | required |
| claim-specificity | The claim comment's own text. | Pass if it names the specific issue/behavior being investigated and a concrete next step or intent, in terms that only fit this issue. Fail if it is interchangeable boilerplate that could be pasted onto any issue (a bare "+1, assign me", flattery plus a guaranteed timeline, generic enthusiasm with no reference to the issue's actual content). | required |
| disclosure-conventions | The repo-facts block's stated AI-use/contribution policy, read against whether the claim comment and repro report disclose AI assistance. | Pass if the repo's stated policy requires no disclosure (silent or permissive) and none is given, or if the policy requires disclosure and the comments name the tool and the extent of assistance. Fail only if the stated policy requires disclosure of AI usage and the comments contain none. | required |
| template-conformance | The repo-facts block's stated bug-report template fields, read against what the repro report covers. | Pass if the report's content covers the fields the template asks for, even out of order or tersely stated. Never changes the verdict either way; it flags a gap worth mentioning, not a reason to hold the package. | preferred |

## Verdict rule

Accept if every required check passes. A `fail` or `unclear` on any required check holds the package (verdict: reject). Preferred checks are reported but never change the verdict. `unclear` on a required check is treated as `fail`: proof that cannot be verified is proof that is not ready to post.
