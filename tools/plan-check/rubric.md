# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| grounded-diagnosis | The plan's stated cause (its diagnosis line), read against every step, artifact, and control run in the repro evidence. | Pass if the stated cause is consistent with every result the repro evidence shows, including its control runs, and names a place where the failure happens. Fail if any repro step or control rules the blamed component out (for example, a control shows the same input behaving correctly with the blamed component in play, or shows the failure already present before the blamed component runs), or if the plan names no cause at all. A cause copied from the issue or thread still fails if the package's own evidence contradicts it. | required |
| bounded-scope | The plan's in-scope list, approach steps, and files/areas, read against the behavior the issue reports and the repro reproduces. | Pass if every change the plan commits to is needed to fix the reproduced behavior (plus its regression tests). Explicitly deferred or "not in scope" work does not count against it. Fail if the plan also commits to work the issue never asked for: a migration, a dependency swap, a new option or setting, a rewrite or restructure of the surrounding module, a redesign, or "while in the area" fixes to other bugs, even when the core fix inside it is correct or the extras are offered as a PR series. | required |
| executable | The plan's approach steps and its named files, modules, or functions. | Pass if a stranger could start the work today: the plan has chosen one approach and names where the change goes (a file, module, or code path). Pinning exact functions later is fine if the file/area and the approach are already chosen. Fail if the plan leaves the main decision open ("X or Y, whichever is easier", "not sure which layer", "somewhere"), or if its only action is to investigate, profile, or poke around without a chosen change. | required |
| decisive-test | The plan's test plan, read against the repro evidence's steps and the actual/expected lines. | Pass if the test plan names at least one specific, observable result that shows the reproduced bug is fixed, normally the repro steps (or the issue's test case) re-run with the expected output, exit code, or behavior stated. Fail if the only success signal is generic ("the full test suite passes", "nothing else breaks", "should feel fast") or names no observable outcome for the fix itself. | required |
| thread-and-convention | The plan comment and plan, read against the thread highlights (maintainer/owner/collaborator comments) and the repo-facts contribution policy. | Pass if all of these hold: (a) when a maintainer, owner, or collaborator in the thread has given explicit direction (identified the culprit code, proposed or rejected an approach, posted a test build or patch, or pointed at an open PR), the plan follows it or the comment openly engages it and says why it differs; (b) when the contribution policy requires AI-use disclosure that covers issue comments or "all AI usage in any form", the comment contains a disclosure naming the AI tool and the extent of its use (treat every package as AI-assisted work). Fail if (a) the plan heads elsewhere without acknowledging that direction, or (b) required disclosure is missing. Disclosure asked only "in the pull request", or no stated disclosure requirement, does not apply to a plan comment. With no maintainer direction and no applicable disclosure rule, pass. | required |
| honest-unknowns | The plan's risks/unknowns statement and any deviations section, read against what the repro evidence does not establish. | Pass if what the evidence does not settle (untested platforms, unmeasured cost, functions not yet pinned) is stated as an unknown or risk, not asserted as fact. Fail if the plan claims certainty the package's evidence does not support. | preferred |

## Verdict rule

Accept if every `required` check passes. Reject if any `required` check
fails. An `unclear` grade on a required check counts as a fail: a plan
whose readiness cannot be shown from the package is not ready to build
from. `preferred` checks are reported but never change the verdict,
whether they pass, fail, or are unclear. The deciding check for a reject
is the first failing required check in table order.
